## 1.1 两种语言如何对照

`testdata/vectors.json` 由 TypeScript 生成，两侧都必须对同一份数据给出一致结果。Go 的 `TestSharedVectors` 逐项断言：

| 向量组 | 断言内容 |
| --- | --- |
| `keys` | 私钥导出的压缩公钥（hex 与 base64url） |
| `rfc8785` / `numbers` / `jcs` | 规范形式与 RFC 8785 附录 B 数字序列化 |
| `reject`（22 条） | 同一输入在同一语言里必须以同一错误码被拒 |
| `requests` | 规范字节、待签名字节、摘要、请求 ID、签名、完整信封 |
| `responses` | 同上，并校验 `reply_to` 等于某条请求的请求 ID |
| `trimmedResponses` | 同上；并断言基础读取器拒绝该形态、基础响应不是精简响应 |
| `trimmedResponsePrefix` | 精简响应用独立前缀，不是基础前缀 |

两侧使用同一组固定测试身份（alice/bob/carol/mallory/one/orderMinusOne），所以任一语言的失败都能在另一语言里复现。

## 2. 方法

消融变体只存在于 `typescript/test/ablation.test.ts`，库内没有"不验签"之类的生产开关。

- **有注入点的实验**（实验 7）直接驱动真实代码路径，只替换去重存储。
- **没有注入点的实验**（实验 1、2、3、4、6）用同一批导出原语在测试内重建处理流程的对应步骤，并删除其中一步。
- **对照实验**保证这种重建是忠实的：把同一批输入分别送进 `RoundtripCore` 和未删除任何步骤的重建流程，两者对 7 类输入给出完全相同的判定码（接受、错误收件人、过期、签名错误、JSON 语法错误、未知顶层字段、重复键）。
- 其余实验（5、8、9、10、11、12）作用在真实实现的既有行为上，不需要重建流程。

## 3. 逐项结果

| 实验 | 删除内容 | 失效的需求 | 观察到的失败证据 | 决定 |
| --- | --- | --- | --- | --- |
| 1 | 请求验签 | 接收方无法知道消息是谁发的 | 伪造 `from = alice`（用 mallory 的密钥合法签名）的请求：基线返回 `ERR_SIGNATURE`、业务执行 0 次；删除验签后业务执行 1 次，且响应 `to` 为 alice 的公钥 | 保留并强制验签 |
| 2 | `to` 检查 | 消息不能误发给别的节点 | alice 合法签署给 carol 的请求送到 bob：基线 `ERR_RECIPIENT`、执行 0 次；删除收件人检查后 bob 执行 1 次。另行确认：只删除收件人检查时，改投 `to` 的请求仍因签名不覆盖新收件人而失败 | 保留收件人检查，且 `to` 必须进入签名 |
| 3 | 响应验签 | 响应确实来自对方 | mallory 冒名 bob 签出 `{sent: 1000.00000000}`：基线抛 `ERR_SIGNATURE`；删除后调用以该伪造结果完成 | 保留并强制验签 |
| 4 | `reply_to` 校验 | 响应关联到正在等待的请求 | 用上一次调用**真实且合法签名**的旧响应去完成新调用：基线 `ERR_RESPONSE_REPLY_TO`；删除后新调用拿到旧账户 A 的结果并认为成功 | 保留 `reply_to` 及其签名覆盖 |
| 5 | `nonce` | 两次新调用可区分 | 两次相同业务调用共用同一 nonce 时摘要相同：基线（每次新 nonce）两次都执行；删除后第二次返回 `REQUEST_ALREADY_SEEN`，合法调用方拿不到结果 | 保留 `nonce` |
| 6 | `expires` | 旧请求不再执行 | 一小时前有效的请求重放：基线 `ERR_EXPIRED`、执行 0 次；删除过期判断后执行 1 次。另行确认去重记录的保留期限由 `expires + 允许时钟误差` 推出 | 保留 `expires` 与最大有效期窗口 |
| 7 | 原子去重 | 并发重复不得重复执行 | 8 次并发投递同一请求：基线（`MemoryReplayGuard`）业务执行 1 次；换成非原子 `claim` 后执行 8 次 | 保留原子认领 |
| 8 | JCS 规范编码 | 跨实现待签名字节一致 | 同一消息两种键序：JCS 下规范字节相同、摘要相同；改用保留插入顺序的写法后两种拼写产生不同字节、不同摘要，且按非规范字节生成的签名在接收方验签失败 | 保留 JCS |
| 9 | 独立 `id` / `type` / `version` | —— | 线上字段只有 `body, expires, from, nonce, sig, to`（响应为 `body, from, reply_to, sig, to`），无 `id`/`type`/`version`/`alg`/`kid`；在此前提下四条需求全部成立：接收方从签名得知发送者、发送方指定并签入收件人、关联完全依赖请求摘要、两次相同调用靠 nonce 区分 | 确认不需要，不添加 |
| 10 | 身份握手 | 双方互相确认身份 | 全新实例、无任何预交换：仅 1 次请求 + 1 次响应，服务端从签名请求学到调用者公钥，调用方从签名响应学到服务端公钥 | 确认不需要握手 |
| 11 | 全局等待表 | 并发调用各自拿到自己的结果 | 5 个并发调用，传输层逆序应答：每个调用拿到的都是自己参数的回显 | 确认不需要等待表 |
| 12 | 第二种 HTTP 模式 | —— | 只保留完整签名壳：一次 POST 完成往返、请求摘要仍计算、`nonce`/`expires`/去重仍在、重复投递被拒；无 `reply_to` 的精简响应被基础接收器以 `ERR_ENVELOPE_FIELD_MISSING` 拒绝 | 确认首版不需要模式切换 |

本轮修复的缺陷（均由上述测试暴露）：

1. 共享向量生成器用 alice 的密钥给 `from` 为 carol、mallory 的两条向量签名，导致 9 条向量中 2 条签名无法用 `from` 验签，跨语言锚点失效。现在向量签名者由 `from` 决定，并在生成时断言签名可验签。
2. **两种语言的时钟偏差默认值不一致**。TypeScript 的默认允许时钟偏差是 5 秒；Go 的 `Config.ClockSkewSeconds int64` 用 `>= 0` 判断是否显式设置，零值 0 会覆盖默认值，于是 Go 实际以 0 秒运行，比 TypeScript 早 5 秒拒绝请求——这是一个安全相关窗口上的跨语言分歧。现在 Go 改用 `*int64`，未设置才用默认，显式 0 仍然有效。
3. **Go 的默认去重存储与注入时钟脱节**。`core.New` 创建 `MemoryReplayGuard` 时用的是真实时钟，而核心支持注入时钟，记录可能在请求仍处于有效窗口内被丢弃。现在默认存储接收核心的同一时钟。
4. **两语言去重存储构造接口不对称**。TypeScript 在构造函数接收时钟，Go 需要事后再调用 `SetClock`；时钟不对的存储会静默丢弃记录，这属于安全默认值差异。现在 Go 同样在构造时接收时钟，`nil` 才表示真实时钟。

5. **两处适配层缺陷（TypeScript）**：libp2p 客户端写完请求帧后未半关闭，导致服务端为等待"第二帧"而挂到调用超时；HTTP 入口在超限时先销毁请求再回 413，客户端收到的是套接字错误而不是 413。两者均已修复并有测试覆盖。
7. **Go libp2p 的超时无法终止阻塞读帧（阻断问题，已修复）**。服务端 `serveStream` 与客户端 `Exchange` 都创建了带超时的 context，但原先没有把它作用到读操作上：对端保持 stream 打开却不继续发送时，读会永远停在 muxer 里，context 取消不了，stream 也不会按计划释放。修复方式是新增 `boundStream`：把 context 的期限压进 `stream.SetDeadline`，并在 context 提前结束时 `stream.Reset()`，让阻塞读真正可中断。超时判定用 `timedOut(ctx, err)`——以绑定的 context 为准，而不是依赖 muxer 的错误类型（yamux 返回自己的 `ErrTimeout`，不包装 `os.ErrDeadlineExceeded`，也不是 `net.Error`）。TypeScript 侧原本就没有这个问题：客户端的 abort 监听会 reset stream，服务端把 signal 传进 `readUvarintFrames`。
8. **两种语言的核心都可能在调用超时后接受响应（阻断问题，已修复）**。`send` 原本只在 `exchange` 返回错误时检查超时：注入一个忽略取消、稍后返回合法响应的 exchange 时，核心会把迟到响应验签通过并判为调用成功；而一个永不返回的 exchange 会让调用挂满整个超时之后。修复分两步，两侧同构：把 abort 与 exchange **竞争**（TS `Promise.race` + `aborted(signal)`，Go 在带缓冲的结果通道上 `select`），使期限由核心自身保证，不依赖适配器配合；并在 exchange 返回后、验签前**再次检查**是否已超时或已取消，迟到响应不再被提升为成功。Go 另外加了 `recover`，避免适配器 panic 拖垮进程。
9. **TypeScript HTTP 客户端的非 2xx 响应没有读取上限（已修复）**。原实现在错误路径上调用无界的 `response.arrayBuffer()`，绕过了成功路径的 `maxResponseBytes`；Go 实现已有 `io.LimitReader`。现在两条路径共用 `readBounded`，超过上限即 `reader.cancel()` 并按状态码分类报错。
6. **Go WebRTC Direct 的装配位置**。go-libp2p v0.49 的 WebRTC transport 在构造时读取 `PrivKey.Raw()` 生成 DTLS 证书，而上游 `bitcoin-libp2p` 的 identity adapter 按设计不可提取，因此 `golibp2p.NewHost` 无法直接装上该 transport。上游需求文档已把这一步交给应用显式装配（见其 §4 与能力对照表"Go Direct listener/transport：业务显式装配"）。Go 测试与示例按该约定实现：宿主、Noise 身份、Yamux、Identify 仍由 `golibp2p.NewHost` 提供，只替换 `Raw()`，使证书绑定到一次性材料而非业务密钥。TypeScript 侧不需要这一步，因为上游 TS SDK 自行处理了证书。

## 5. 去重存储的能力边界

- 单进程内存实现：`persistent: false`、`shared: false`、`resultCache: false`，并有测试证明清空（模拟重启）后同一请求会再次执行。库不声称跨重启防重放。
- 多实例：两个核心共享同一去重存储时，并发投递只执行一次（`test/processing.test.ts`）。默认实现不共享，跨实例需要应用提供共享存储。
- **未运行**：本仓库没有持久化去重存储实现，因此"持久化实现必须证明符合它声称的保证"这一项在本版本没有可验证对象。业务侧持久副作用的幂等提交与业务事务的结合也未实现。
- 已完成请求的结果不可取回：重复请求只得到 `REQUEST_ALREADY_SEEN`，这是首版明确限制。

## 6. 环境限制与未完成项

- WebRTC Direct 只在本机 UDP 回环下验证，未验证跨 NAT、跨主机、TURN 或中继场景。真实部署的可达性不在本库承诺内。
- libp2p 侧未实现中继与地址发现：示例用 `peerStore.save` 显式告知对端地址，身份发现不在首版范围。
- HTTPS 精简响应模式：**两种语言的传输层都不做**，但消息层的解析与打包两侧都已提供统一 API（TS `parseTrimmedResponse`/`verifyTrimmedResponse`，Go `ParseTrimmedResponse`/`VerifyTrimmedResponse`，共用 `signingBytes` 与 `encodeEnvelopeBytes`，独立前缀 `roundtrip/http-response/v1\n`）。没有任何适配器会产出或接收它，也没有生产开关；应用若决定使用，必须自行承担"签名不再证明响应回答哪次调用"这一取舍（两侧都把该失效写成了断言）。
- Go 的 WebRTC Direct 依赖一次性证书密钥（见上文第 6 条），因此 Go 侧该承载的 `certhash` 不绑定业务身份；上游 TS SDK 无此限制。这是上游 Go 侧的限制，不是本项目的选择。
- Go 侧未实现：HTTPS 精简响应的传输适配（两侧都未实现）、上游未提供的地址发现与中继装配、持久化去重存储（两侧都只有内存实现）。

## 7. 最终决定

保留的机制：请求验签、收件人检查且 `to` 进入签名、响应验签、`reply_to` 及其签名覆盖、`nonce`、`expires` 与最大有效期窗口、原子去重认领、JCS 规范编码、固定 secp256k1 / 压缩 SEC1 / 严格 DER / low-S、一次调用一个 stream 的 libp2p 承载、完整签名壳的 HTTP 模式、内存去重存储的能力声明。

确认不需要、因而未实现的机制：独立 `id` 字段、独立 `type`/`version` 字段、身份握手、全局等待表与响应分发循环、HTTPS 精简响应的传输适配、ACK、心跳、会话、自动重试、响应缓存。精简响应的消息层对照实现见第 6 节。

本轮交付的阶段状态：阶段 1–6 在两种语言中都完成并有测试覆盖。TypeScript 与 Go 各有一套最小示例（TS `typescript/examples/`，Go `core/example_test.go` 中的两个 Example 函数，输出由测试校验）。共享向量是两侧的唯一测试数据契约，两侧都通过。
