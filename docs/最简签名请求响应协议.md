# 最简签名请求响应协议

本文依据 `原始需求.md` 和讨论整理，不修改原始需求。本文是设计规范；对应的消融实验已实现并运行，结果见[消融测试结果](消融测试结果.md)。

## 1. 目标与边界

在 WebSocket、WebRTC、libp2p 和 HTTP(S) 上提供一次请求、一次响应的交互。消息用私钥签名；私钥不进入消息。

协议保证：

- 接收者能够验证发送者控制着声明的公钥。
- 发送者明确指定接收者；送错接收者的消息不得执行。
- 响应来自指定对方，并关联到正在等待的请求。
- 重复投递不能绕过去重检查，导致同一请求并发重复执行。

公钥是协议身份，不自动证明现实中的姓名或组织。预期接收者公钥由调用方提前获得并信任；身份发现不在首版范围内。验签不等于授权，业务仍须根据已验证的公钥判断权限。

签名不提供保密。普通 HTTP 上的消息可以被读取。保密依赖安全传输；首版不加入消息加密和密钥协商。

## 2. 基础消息壳

请求：

```json
{
  "from": "<A公钥>",
  "to": "<B公钥>",
  "nonce": "<随机值>",
  "expires": 1790000000,
  "body": {
    "op": "get_balance",
    "args": {}
  },
  "sig": "<A签名>"
}
```

响应：

```json
{
  "from": "<B公钥>",
  "to": "<A公钥>",
  "reply_to": "<请求摘要>",
  "body": {
    "ok": true,
    "result": {}
  },
  "sig": "<B签名>"
}
```

| 字段 | 含义 |
| --- | --- |
| `from` | 发送者公钥，也是验签依据 |
| `to` | 明确的接收者公钥，必须参与签名 |
| `nonce` | 每次新请求生成的随机值，区分内容相同的两次调用 |
| `expires` | 请求过期时刻，Unix 秒，整数 |
| `reply_to` | 完整请求的摘要，也是请求 ID |
| `body` | 应用内容，整体参与签名 |
| `sig` | 发送者对消息的签名 |

请求必须包含 `nonce`、`expires`，不得包含 `reply_to`。基础响应必须包含 `reply_to`，不得包含 `nonce`、`expires`。不设置独立的 `type`、`id` 或 `version` 字段。首版拒绝未知顶层字段，扩展放在 `body` 中。

`body.op` 和业务参数由应用定义。成功响应采用 `{"ok":true,"result":...}`，业务失败采用 `{"ok":false,"error":{"code":"...","message":"..."}}`。响应错误同样签名。

## 3. 规范编码、签名与请求 ID

首版采用 JSON + JCS（RFC 8785），不自行实现一套只排序键的 JSON 规则，也不采用未限定编码方式的 CBOR。

JCS 规定对象键排序、数字和字符串编码等规则。JSON 的空白和对象键排列不同，不影响规范化后的字节。数组顺序仍然有意义，不能排序数组。字符串不擅自进行 Unicode 归一化。

```text
unsigned   = 消息去掉顶层 sig 后的对象
bytes      = UTF8("roundtrip/v1\n") || JCS(unsigned)
sig        = Sign(private_key, bytes)
request_id = base64url(SHA256(bytes))   // 仅对请求计算
```

`JCS(unsigned)` 输出 UTF-8 字节。`||` 表示字节拼接。固定前缀同时隔离协议和版本，不加入线上版本协商。

接收者用相同规则复现 `bytes`，再用 `from` 的公钥验证 `sig`。接收者不重新生成签名，也不需要发送者私钥。

请求摘要就是请求 ID，不是另一个字段。摘要覆盖 `from`、`to`、`nonce`、`expires`、`body` 和协议前缀，不覆盖 `sig`。两次内容相同的新调用因为 `nonce` 不同而得到不同 ID；同一请求重传则保持相同 ID。

发送者维护：

```text
请求 ID → 原请求、预期响应者、等待结果的调用
```

接收者计算同一个请求 ID，填入响应的 `reply_to`。响应签名覆盖 `reply_to`，防止关联关系被篡改。

### 编码约束

- 拒绝重复 JSON 键、无效 Unicode 和不符合 JCS 的输入。
- JSON 数字遵守 JCS 的数值约束；金额、大整数等精确数据用业务约定的字符串表示。
- `nonce` 使用密码学安全随机源，至少 128 位。
- 二进制值和摘要使用无填充 base64url；公钥必须只有一种规范表示，避免同一公钥出现多种身份字符串。
- 首版固定 secp256k1、公钥压缩 SEC1、严格 DER 与 low-S 签名，不增加 `alg` 协商字段。签名实现对 `bytes` 做一次 SHA-256 后签摘要，禁止二次哈希；详细私钥接入和测试向量要求见 [施工单](施工单.md)。
- 最大消息大小、最大有效期窗口和允许时钟误差的首版默认值见施工单；接收端按本地限制验证，不进行在线协商。

参考：[RFC 8785：JSON Canonicalization Scheme](https://www.rfc-editor.org/rfc/rfc8785.html)。

## 4. 接收与响应规则

接收请求时：

1. 校验结构、大小、有效期及最大有效期窗口。
2. 检查 `to` 是自己的身份。
3. 使用 `from` 验签。
4. 原子登记请求 ID，再进行授权和业务执行，避免并发重复请求穿透。
5. 返回签名响应。

去重记录区分执行中和已完成。重复请求不得再次执行业务；可以等待已有结果、返回已缓存的签名响应，或返回明确的重复请求错误。已完成记录至少保留到请求不再可能通过有效期检查，包括允许的时钟误差。

进程重启、多实例部署不能各自清空或割裂去重状态后仍声称防重放。有副作用的业务需要持久化、共享的去重记录，并处理登记与业务提交之间的事务一致性。协议壳本身不承诺跨崩溃的恰好执行一次。

接收基础响应时，必须同时检查：

```text
response.to       == 自己
response.from     == 原请求.to
response.reply_to == 正在等待的请求 ID
签名有效
```

一个等待调用只完成一次。未知、已完成或已超时请求的响应不得交给其他调用。

收到有效响应，能确认对方参与了这次交互。没有响应，不能判断请求是否到达或业务是否执行。首版不自动重试；同一请求重传必须保留原消息，新调用才生成新 `nonce`。

## 5. WebSocket、WebRTC 与 libp2p 适配

| 传输 | 消息边界 |
| --- | --- |
| WebSocket | 一条完整 WebSocket 消息承载一个壳 |
| WebRTC DataChannel | 一条消息承载一个壳，首版使用可靠、有序通道 |
| libp2p 字节流 | 用长度前缀切分消息，读取前检查长度上限 |

双方都可以主动发请求。多次调用共享连接时，通过请求摘要和 `reply_to` 匹配响应，不增加会话、序号、ACK、心跳或自动重试协议。首版实现只接上游 libp2p stream，每次调用一个 stream；WebSocket/WebRTC 由上游承载，不另做裸通道适配，具体边界见施工单。

## 6. HTTP(S) 单独适配

HTTP 已经把一个响应绑定到一个请求，因此可以省掉应用层的一部分关联工作。不过，HTTP 的调用关联与签名的密码学关联是两件事。

### 6.1 默认：完整签名壳

```text
POST /roundtrip
Content-Type: application/json

正文：签名请求壳

HTTP 响应正文：签名响应壳
```

业务操作放在 `body.op`，固定 URL 负责找到服务，`to` 负责指定身份。HTTP 方法与路径不决定另一个未签名的业务操作。

HTTP 客户端直接等待本次 POST 的返回值，因此不需要维护按请求 ID 查询的全局等待表，也不需要独立分发响应的循环。服务端仍计算请求摘要，放进 `reply_to`。

默认仍保留响应 `reply_to`：普通 HTTP 的攻击者可以把以前的合法签名响应替换到当前请求上。如果没有关联字段，旧响应的身份和签名依然可能通过。HTTP 本身的一来一回不能阻止这个替换。

这也是兼容 HTTP、跨传输转发和独立验签时最统一的模式。

### 6.2 可选：受信 HTTPS 通道的精简响应（不进入首版施工）

当应用明确接受下面的约束时，HTTP 适配可以删除响应的 `reply_to`：

- 客户端验证 HTTPS 服务端身份；预期服务端与目标公钥之间有可信配置绑定。
- TLS 终止端及其到实际处理端的路径都在信任范围内。
- 响应只在本次 HTTP 调用内使用，不转发为基础协议响应，也不作为可独立证明请求关联的凭据。
- 双方通过端点配置固定使用此模式，不进行动态协商。

此时响应变为：

```json
{
  "from": "<B公钥>",
  "to": "<A公钥>",
  "body": {
    "ok": true,
    "result": {}
  },
  "sig": "<B签名>"
}
```

它采用独立签名前缀 `roundtrip/http-response/v1\n`，避免被当作基础请求或基础响应接受。请求仍使用基础请求格式和前缀。客户端从当前 HTTP 调用取得原请求，检查响应 `from`、`to` 和签名；请求关联依赖受信 HTTPS 通道。

**删掉 `reply_to` 后，响应签名本身不再证明它回答了哪次请求。** 这是明确的能力取舍，不是字段含义变了。普通 HTTP 不允许使用此精简模式。HTTP 调用超时后，迟到响应也不得转交其他调用。

### 6.3 HTTP 中哪些可以删，哪些仍要保留

| 机制或字段 | HTTP 适配决策 |
| --- | --- |
| 等待表、响应分发循环 | 可以删，由每次 HTTP 调用管理等待 |
| 响应 `reply_to` | 默认保留；只有上述受信 HTTPS 精简模式可删 |
| 请求摘要计算 | 仍保留，用于服务端去重；精简模式不必把它放进响应 |
| 请求 `nonce`、`expires`、去重状态 | 保留，HTTP 不阻止合法签名请求被再次投递 |
| `from`、`to`、`sig` | 保留，满足消息级公钥身份和收件人约束 |
| 额外 ACK、连接会话、序号 | 不加入 |

### 6.4 HTTP 状态与错误

已接受并完成协议处理的调用返回 HTTP 200，正文用签名壳表示业务成功或失败。格式、大小、认证等入口错误可用 4xx，基础设施错误可用 5xx；不能把无签名的状态码或代理错误页当成对方签名的业务结果。

断线和超时表示没有拿到有效响应，不表示业务没有执行。HTTP 自动重试不得生成新请求冒充原调用，也不得绕过服务端去重。

普通 HTTP 服务端无法凭现有请求连接任意主动发起反向请求。如果双方都需要主动调用，双方各自提供可达 HTTP 入口，或采用双向传输；首版不加入长轮询。

## 7. 消融测试：逐项删除，检验必要性

先实现满足目标的基线，每次只删除一个字段或机制，运行同一套测试。必要约束失效则恢复；仍通过则删除。下表是预期结果，不是已运行的测试报告。

| 删除项 | 测试 | 预期结论 |
| --- | --- | --- |
| 签名 | 伪造身份、修改业务内容 | 失败，保留 |
| `to` 或对它的签名覆盖 | 把发给 B 的请求投递给 C，或篡改目标 | 失败，保留并签入 |
| 响应签名 | 注入伪造结果 | 失败，保留 |
| 基础响应 `reply_to` | 交换并发响应、回放旧响应 | 失败，保留 |
| HTTP 完整模式 `reply_to` | 在普通 HTTP 上替换为旧的合法响应 | 失败，保留 |
| 受信 HTTPS 模式 `reply_to` | 在可信调用中并发请求并核对各自结果 | 可删除，但失去独立签名关联能力 |
| `nonce` | 连续两次相同业务调用 | 新调用与重放不可区分，保留 |
| `expires` | 去重记录清理后回放旧请求 | 旧请求可执行或记录无法有界清理，保留 |
| 去重状态 | 并发投递同一个请求 | 可能重复执行，保留 |
| 规范编码 | 改变 JSON 键顺序和空白 | 跨实现验签可能失败，保留 |
| 独立请求 `id` | 改用完整请求摘要关联 | 仍通过，删除 |
| 独立 `type`、`version` | 严格结构和固定签名前缀 | 仍通过，删除 |
| 身份握手 | 首条请求直接携带公钥并签名 | 身份目标仍满足，删除 |
| ACK、心跳、会话、自动重试 | 单次调用及超时 | 核心目标仍满足，不加入 |

还需测试：

- 修改任意一个签名字段后验签失败。
- 两次相同业务请求使用不同 nonce，得到不同请求 ID。
- 重复请求并发到达、进程重启、多个实例接收时，不能重复产生副作用。
- 从 WebSocket 捕获请求再投递到 HTTP，只能被相同 `to` 接受，并共享去重状态。
- 已超时或已完成请求的响应不能完成另一次调用。
- HTTP 精简响应不能被基础协议接收器接受。
- 在真实跨语言实现中验证 JCS、摘要、公钥编码和签名测试向量一致。
