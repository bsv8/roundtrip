# 最简签名请求响应协议施工单

依据：[原始需求](原始需求.md)、[最简签名请求响应协议](最简签名请求响应协议.md)。本文规定实现边界、施工顺序和验收方式。实现与验收结果见[消融测试结果](消融测试结果.md)。

## 1. 边界决策

协议核心与 bitcoin-libp2p 无关，第一份实际传输适配接 bitcoin-libp2p。不要为了“上游无关”建立插件系统、通用事件总线或传输注册中心。

```text
应用：选择身份、取得目标公钥、授权、执行业务、选择去重存储
                         │
roundtrip：规范编码、签名壳、验签、请求关联、去重协调、调用生命周期
                         │
适配：bitcoin-libp2p stream / HTTP
                         │
上游：连接建立、认证、传输安全、流复用、连接生命周期
```

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| bitcoin-libp2p | PeerId、Noise、连接、WebSocket/WebRTC、libp2p stream | roundtrip 消息、业务签名、业务请求去重 |
| roundtrip 核心 | 消息结构、JCS、摘要、验签、目标检查、响应关联、处理流程 | 拨号、SDP、地址发现、身份发现、钱包管理 |
| 传输适配 | 收发完整消息、帧边界、大小限制、取消与流清理 | 改写签名字段、跳过验签、业务重试 |
| 应用 | 目标公钥信任、业务权限、业务处理、持久化策略 | 自行实现另一套签名编码 |
| 签名实现 | 在固定协议用途下签名，提供自己的公钥 | 把私钥交给核心或网络对端 |

已检查上游 `docs/identity-profile-v1.md`、`typescript/src/signer/index.ts` 和 `typescript/src/stream/index.ts`：身份采用 secp256k1；SDK 的 TypedSigner 只允许 Noise 和 Peer Record 两种用途，并未提供业务签名。不能把 roundtrip 内容伪装成这些用途。施工默认不修改上游。

## 2. 私钥如何引入

### 2.1 最小入口：应用注入签名者

核心只拿公钥和签名能力，不拿原始私钥。建议接口如下，语言类型只是表达边界：

```ts
interface RoundtripSigner {
  publicKey(): Uint8Array
  signRoundtrip(unsigned: UnsignedEnvelope, signal?: AbortSignal): Promise<Uint8Array>
}
```

`UnsignedEnvelope` 是本协议严格校验后的请求或基础响应结构，不是任意 JSON。签名实现仍须独立校验，并在自己的可信执行范围内完成 JCS、固定协议前缀和哈希。不得提供网络可调用的通用 `sign(bytes)` 服务。

核心根据 `publicKey()` 自动设置 `from`，业务调用不能自行指定 `from`。签名结果返回后，核心本地验签再发送，发现签名者配置或编码不一致时立即失败。实例的身份固定；替换身份时创建新实例。

首版只实现本地签名者，不实现远程签名 RPC、硬件钱包、浏览器 Worker 或钱包插件。现有部署必须使用隔离签名者时，把这个接口接入已有隔离环境，不能退回到向不可信环境暴露私钥。

### 2.2 复用同一身份，但不复用错误的签名用途

如果应用本来持有 bitcoin-libp2p 的业务身份私钥，由应用在可信启动阶段分别配置上游身份和 roundtrip 本地签名者。使用同一公钥可以避免额外的身份映射。

如果应用只有上游 TypedSigner、拿不到私钥，它目前就不能完成 roundtrip 消息签名。接入工作必须在实际持钥的一侧增加明确的 `signRoundtrip` 能力；roundtrip 无法也不应从连接或公钥恢复私钥。没有这项能力时，报告“不支持业务签名”，不静默创建第二个身份。

roundtrip 不生成、保存、导出或轮换用户的生产私钥，不读取环境变量或密钥文件来猜测身份，不从上游内部对象提取私钥。测试和示例可以生成临时密钥，必须明确其临时性质。

### 2.3 首版固定密码学约定

为直接接上游，首版采用其身份格式：

- 私钥为有效的 32 字节 secp256k1 标量，仅在签名实现中使用。
- 公钥为 33 字节压缩 SEC1 点，线上 `from`、`to` 使用无填充 base64url 编码。
- 消息签名为 ECDSA secp256k1，严格 DER 编码、low-S，线上 `sig` 使用无填充 base64url。
- 对 `UTF8("roundtrip/v1\n") || JCS(unsigned)` 做一次 SHA-256，然后签这个摘要；验签采用相同规则，禁止二次哈希。
- 请求 ID 是同一个摘要的无填充 base64url，不包含签名。

这与上游本地签名实现的哈希、DER 验证方向一致，但具体依赖 API 必须通过固定测试向量确认，不能仅凭函数名称判断是否内部预哈希。

不增加算法协商、证书、密钥 ID、独立 PeerId 字段或第二套身份协议。密码库使用成熟实现，roundtrip 不自行实现曲线运算。

## 3. 上游适配怎么切

### 3.1 第一版只接 libp2p stream

WebSocket 和 WebRTC 在上游已经是 libp2p 的承载方式，roundtrip 不再各写一套 SDP、连接或 DataChannel 适配。

应用提供已建立连接，或传入使用上游 API 打开 stream 的函数。roundtrip 注册固定应用协议 `/roundtrip/1`，每次调用打开一个 stream：

```text
打开 stream → 写一帧请求 → 读一帧响应 → 关闭 stream
```

帧边界复用上游 uvarint 分帧工具。一个 stream 只允许一条请求和一条响应；额外帧为协议错误。若连接支持复用，并发调用由上游多个 stream 承载，不在 roundtrip 再建多请求复用器或全局响应分发器。

此处比通用消息通道更简单，但完整响应仍保留 `reply_to`，使消息壳的关联规则不依赖 stream。

第一版不做直接 WebSocket 或裸 DataChannel 适配。协议仍然可以独立使用，以后确有需求再增加适配；这不影响核心独立。

### 3.2 连接身份与消息身份

首版 libp2p 适配为直连模式：

- 发起调用前，连接认证的远端公钥必须等于目标 `to`。
- 接收请求时，请求 `from` 必须等于连接认证的远端公钥。
- 接收响应时，响应 `from` 必须同时等于原请求 `to` 和连接认证的远端公钥。

PeerId 转公钥等处理调用上游原生能力，不自行拼装 PeerId。连接认证不代替消息验签。

这里的“直连”指业务对端就是连接认证对端，允许上游底层使用中继建立端到端认证连接。首版不支持一个业务身份代另一个身份转发签名请求；以后若需要应用级转发，要单独定义信任边界。

## 4. HTTP 适配怎么切

第一版只实现协议文档中的完整模式：固定入口 `POST /roundtrip`，请求和响应正文都使用完整签名壳。

- HTTP 原生负责调用等待，不设全局等待表。
- 仍保留响应 `reply_to`，请求 `nonce`、`expires` 和服务端去重。
- 每个 HTTP 请求直接进入与 libp2p 相同的验签、授权、去重、业务处理流程。
- `body.op` 是唯一业务操作依据，URL 或未签名头不得切换另一种业务。
- HTTP 适配不读取或管理私钥，只使用注入的签名者。
- 共享同一个处理器和去重存储时，跨 HTTP/libp2p 的重复投递也要被识别。

HTTPS 精简响应不进入首版 HTTP 适配。虽然可以删除 `reply_to`，却需要受信 TLS 终止、目标公钥绑定、独立签名前缀和另一套接受规则。首版 HTTP 调用保留完整响应。两侧已有精简响应的消息层解析、签名与验签，用于协议对照；适配器不得产出或接收它。

HTTP 业务完成返回 200 和签名业务结果；入口与基础设施错误采用适当的 HTTP 错误，不当成签名业务响应。超时不能解释为业务未执行。客户端和代理不得自动重试有副作用的调用。

## 5. 核心最小职责与接口

不要为了分层把每个函数都做成可替换插件。核心内部固定一套编码、摘要和验签实现，暴露调用与处理入口即可：

```text
call(to, body, exchange, options) → 已验证的业务响应
handle(requestBytes)             → 签名响应字节
```

`exchange(requestBytes, signal)` 表示一次完整请求响应的搬运：返回响应字节，不处理签名与业务。libp2p 和 HTTP 分别提供它。上游连接身份检查留在 libp2p 适配，因为通用核心没有 PeerId 概念。

应用业务处理接口：

```text
handler({ callerPublicKey, requestId, body }) → 成功或业务错误
```

只有结构、目标、签名和去重检查通过后才可进入 handler。应用在 handler 内进行授权，不再单独设计一个授权框架。

### 去重边界

去重存储是唯一必要的状态接口：原子认领请求 ID、记录完成结果、保存至有效期结束。超时取消不释放认领记录，让重复请求有机会重新执行业务。

首版重复请求统一返回签名的 `REQUEST_ALREADY_SEEN`，不等待执行中请求，不建设响应缓存或重试恢复服务。已完成结果记录可以是最小完成标记；无法凭此重新取回业务结果，是首版明确限制。

库提供单进程内存实现，适用于演示和无持久副作用场景。生产业务的持久化、跨实例原子性由应用提供。持久副作用的幂等提交必须与业务事务结合；不声称简单存储接口已经解决跨崩溃一致性。

建议首版默认：最大消息 1 MiB、请求有效期 60 秒、最大有效期窗口 60 秒、允许时钟误差 5 秒、调用超时 15 秒。部署可显式配置；接收端按自己的限制拒绝输入，不增加在线协商。去重记录保存到 `expires + 允许时钟误差`。调用超时只结束本地等待。

## 6. 按阶段施工与验收

### 6.0 双语言范围（2026-09-28 修订）

本项目是双语言对照项目：TypeScript 与 Go 两侧都有对应实现，全部机制与测试数据一一对应。
TypeScript 与 Go 均进入首版，本节为现行约定：

- **共享测试数据是唯一契约**。`testdata/vectors.json` 由 TypeScript 生成，包含密钥、RFC 8785 数字、JCS 用例、22 条严格读取拒绝用例、请求、基础响应与精简响应向量。两侧都必须对它给出一致的规范字节、待签名字节、摘要、请求 ID、签名与完整信封，错误码也必须一致。
- **两侧的测试身份相同**。两侧使用同一组固定私钥（alice/bob/carol/mallory/one/orderMinusOne），因此任一语言的失败都能在另一语言里复现。
- **机制对照，不追求形式对称**。传输装配按各自上游 SDK 的形态：TypeScript 用 `createHost`，Go 用 `golibp2p.NewHost`；Go 的 WebRTC Direct transport 由应用显式装配（上游需求文档已把这一步交给业务，因为 go-libp2p 会读取 `PrivKey.Raw()`）。
- **精简响应只做消息层**。两侧都提供解析、打包、签名与验签，基础接收器都拒绝该形态；两侧都不提供传输适配与生产开关。

阶段划分对两侧同时成立。

| 阶段 | 交付内容 | 验收门槛 | TS | Go |
| --- | --- | --- | --- | --- |
| 1：固定编码 | 严格 JSON 解析、JCS、公钥/签名编码、请求摘要、固定向量 | 改键顺序和空白不改摘要；重复键必须拒绝；数字边界明确 | `core/json.ts` `jcs.ts` `envelope.ts` | `core/json.go` `jcs.go` `envelope.go` |
| 2：签名核心 | 签名者接口、本地实现、签名和验签、目标检查 | 篡改任何字段失败；错目标不进 handler；错误签名者配置失败 | `core/signer.ts` | `core/signer.go` |
| 3：处理流程 | handler、原子去重、超时与取消、重复错误 | 并发重复只有一次进入业务；旧响应不能完成新调用 | `core/core.ts` | `core/core.go` |
| 4：libp2p 适配 | 每次调用一个 stream、上游分帧、连接身份校验 | WebSocket 与 WebRTC 承载下同一壳可往返，资源正常释放 | `src/libp2p/` | `go/libp2p/` |
| 5：HTTP 适配 | 完整壳 POST、同一处理流程 | HTTP 往返成功；旧响应替换失败；跨传输重复请求不重复执行 | `src/http/` | `go/http/` |
| 6：消融收口 | 基线、逐项删除实验、结果文档、最小示例 | 保留每项机制都有失败证据；删除项仍满足需求 | `test/ablation.test.ts` | `core/ablation_test.go` |

测试不得以正常往返成功代替攻击、重复和错误路径的验收。真实 WebRTC 测试如需额外运行环境，报告环境和未完成项，不用模拟通过冒充真实适配通过。

建议文件职责：`core`、`signer`、`replay`、`adapters/libp2p`、`adapters/http`、`tests`。不提前创建空的其他适配目录，不引入插件注册系统。两侧按同一职责划分对应文件，见上表最后一列。

## 7. 消融测试必须交付

消融不是把代码注释掉后只跑成功用例。每个实验必须说明：删掉什么、其余条件是否相同、哪个需求失效、失败的具体证据。消融变体只用于测试，不通过生产开关暴露“不验签”等选项。

| 实验 | 必须观察的结果 |
| --- | --- |
| 删除签名验证 | 伪造 `from` 能进入 handler，说明身份保证失效 |
| 删除 `to` 检查或签名覆盖 | 错投或改投能执行，说明收件人保证失效 |
| 删除响应签名 | 伪造成功响应能完成调用 |
| 删除 `reply_to` 校验 | 合法旧响应能完成新调用；不能只测随机伪造响应 |
| 删除 nonce | 同内容的两次新调用摘要相同，第二次被误判重复 |
| 删除 expires | 清理记录后，旧请求仍能执行 |
| 删除原子去重 | 同一请求并发进入两次 handler |
| 删除 JCS | 不同 JSON 表达或不同实现产生不一致的待签名字节 |
| 删除独立 id/type/version | 基线约束仍通过，证明不需要这些字段 |
| 删除身份握手 | 首条签名请求仍能完成双向身份验证 |
| 删除全局等待表 | 一次调用一个 stream/HTTP 的并发调用仍正确 |
| 删除第二种 HTTP 模式 | 所有首版 HTTP 需求仍满足，证明首版不需要模式切换 |

其中删除字段的实验需要双方按同一删减格式构造合法签名，不能因为旧解析器报“缺少字段”就宣称机制必要。攻击实验检查是否错误执行业务或错误完成调用。

额外检查去重存储在多实例和重启条件下的行为：内存实现应明确暴露其能力限制；持久化实现必须证明符合它声称的保证。

最终生成 `消融测试结果.md`，记录基线版本、测试环境、每项结果与最终决定。未运行的实验标为未运行，不能写成已验证结论。
